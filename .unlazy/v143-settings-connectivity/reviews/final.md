# Independent post-implementation review

Reviewed the current working tree and the v1.4.3 brief's 13 review questions. This was a source review only: no product files were edited and no tests were run.

## Finding

### [P2] iPad runtime accepts secure negotiation before mutual authentication

`BoothNetworkTransportRuntime.handleCoreSecureHelloOnQueue` passes an inbound Hello directly to the negotiator and can configure keys/send a Ready proof (`Shared/Connectivity/BoothNetworkTransportRuntime.swift:1879-1930`). Neither this handler nor `handleCoreSecureReadyOnQueue` requires `candidate.peerProofSent && candidate.peerProofVerified` (`1932-1981`); `finishCoreSecureChannelIfReadyOnQueue` and `promoteCoreCandidateOnQueue` also do not require those flags (`1984-2029`). The iPad responder negotiator accepts a Mac Hello while in `waitingForAuthoritativeHello` (`Shared/Connectivity/BoothSecureChannelNegotiator.swift:88-149`).

As a result, a selected, trusted iPad candidate can derive keys and emit its transcript-bound HMAC Ready proof before the explicit HMAC authentication exchange completes. A peer still needs the shared secret to produce the matching Ready proof, so this is not evidence of an unauthenticated plaintext downgrade or a trust bypass; it is a violation of the required phase ordering and exposes the trusted-secret proof path before the authentication state says it is complete. Require both auth proofs before processing secure Hello/Ready, and add a regression test that injects secure Hello/Ready before proof completion and confirms rejection without key preparation, Ready output, or promotion.

## Incident and acceptance limits

The attached brief contains the reported symbolic `malformedEnvelope` symptom, but no packet capture, raw control frame, or populated incident log. Therefore the exact first offending frame and the production root cause remain unknown; this review cannot say the reported disconnect is fixed. New diagnostics and regression tests improve future evidence but do not identify the past frame.

This source review did not verify Settings screenshots at the three requested sizes, Thai rendered geometry, physical reconnect behavior, or iPad Pro 9.7 / iPadOS 16.7.16 compatibility. Those acceptance items remain pending separate execution.

## Follow-up: P2 authentication phase finding resolved

The current runtime now requires `mutualAuthenticationComplete` before accepting secure Hello or Ready, establishing the secure channel, or promoting the candidate (`Shared/Connectivity/BoothNetworkTransportRuntime.swift:1880-1888, 1941-1953, 2001-2009, 2045-2051`). The new real-socket loopback regression sends transport Hello followed by premature secure Hello and verifies rejection, closure, no secure Hello/Ready response, and no authentication (`Tests/NetworkRouteTests.swift:1707-1789`). This resolves the source finding. Coverage caveat: the regression injects early secure Hello, not a separate early Ready frame. No tests were run during this follow-up review.

## Follow-up: early Ready regression coverage added

The loopback regression now runs for both `secureChannelHello` and `secureChannelReady` inputs via test arguments, and asserts each matching runtime rejection reason, connection closure, no secure negotiation output, no authentication, and no prepared keys (`Tests/NetworkRouteTests.swift:1707-1806`). The two cases align with the runtime's pre-authentication guards (`Shared/Connectivity/BoothNetworkTransportRuntime.swift:1880-1888, 1941-1953`), so the earlier Ready-coverage caveat is addressed. No remaining issue identified in this targeted review; tests were not run.
