# iPad reconnect presentation audit

## Scope and evidence boundary

This is a read-only source audit. The attached text describes a recording and connection log, but neither raw artifact is present in the workspace/attachment set; there is no timeline or exported diagnostic to correlate against callbacks. The code below proves how the UI reacts when the transport resets or discovery changes. It does **not** prove why the control connection fails or that a particular UI transition occurred in the reported session.

## State ownership and reset paths

`BoothConnectionStatus` holds both durable-ish peer presentation inputs (`preferredPeerID`, `trustedPeerIDs`) and volatile transport/discovery inputs (`peerID`, `peerDisplayName`, `discoveredPeers`). `publish(...)` overwrites the current connection identity and derives `connectedPeerNames` directly from the possibly nil display name (`Shared/Connectivity/BoothTransport.swift:218-249`). `publishPairing(...)` only changes the preferred ID when `updatePreferredPeer` is true, and only replaces discovered peers when supplied (`Shared/Connectivity/BoothTransport.swift:321-339`). `publishDisconnected()` clears current authentication, connection identity, channels, and route state, but does not clear preferred ID, trusted peers, or discovered peers (`Shared/Connectivity/BoothTransport.swift:341-362`).

`NetworkBoothTransport` seeds the iPad target from the saved preferred ID only when auto-reconnect is enabled (`Shared/Connectivity/NetworkBoothTransport.swift:457-459`), and publishes the saved preferred ID and trusted peer list at initialization (`Shared/Connectivity/NetworkBoothTransport.swift:588-590`, `5448-5465`). The saved preferred ID itself is stored independently in UserDefaults; trusted names are stored as metadata (`Shared/Connectivity/BoothPairing.swift:1570-1617`). Refresh/reconnect does not clear that preference. Explicit peer selection, connection, pairing completion, and forgetting do change it (`Shared/Connectivity/NetworkBoothTransport.swift:1579-1609`, `4970-4985`, `1752-1768`).

There are two source-proven discovery resets:

- The manual `refreshPeerDiscovery()` clears all discovered peer/provenance/route-candidate dictionaries, publishes an empty peer list, and starts a new discovery generation (`Shared/Connectivity/NetworkBoothTransport.swift:1612-1630`).
- `startRouteDiscovery()` does the same on startup and reconnect, then tears down the active transport, sets connection state to `.connecting`, and publishes status (`Shared/Connectivity/NetworkBoothTransport.swift:2302-2327`). A control close on iPad invokes this path (`Shared/Connectivity/NetworkBoothTransport.swift:5857-5909`). Teardown clears `peerName` and `peerDeviceID` and sets the connection state disconnected before the route discovery caller changes it to connecting (`Shared/Connectivity/NetworkBoothTransport.swift:2827-2846`).

The result is a real transient reset of **current connection identity and discovered rows**, while the saved preferred ID and trusted peer metadata remain. `publishPairingStatus()` rebuilds `status.discoveredPeers` from current discovery results and always republishes the stored preferred ID (`Shared/Connectivity/NetworkBoothTransport.swift:3044-3085`, `5448-5465`). Discovery callbacks replace each provenance's current result set; an ID is removed once it has no remaining provenance (`Shared/Connectivity/NetworkBoothTransport.swift:3048-3084`). This can remove and later re-add a row as browse results change. Whether a specific callback sequence produces a visible frame of absence depends on runtime callback timing and is not established without the recording/log.

## Connected truth and view-model state

The view model already has a stronger control-readiness rule than the Settings view uses: for `NetworkBoothTransport`, authoritative control requires `.connected`, authenticated peer, established secure channel, and control activity newer than 10 seconds; full booth readiness further requires preview and verified asset channels (`iPad/UI/iPadViewModel.swift:109-142`). Settings currently labels a peer green when the status is `.connected`, authenticated, and has a name; it shows secure and asset readiness as subordinate rows rather than using the view-model predicate for the green “Connected Mac” identity (`iPad/UI/iPadConnectionSettingsView.swift:208-224`). It does not use the selected preferred ID in that branch. The shared resolver likewise derives `controlConnected` from `status.state` alone but derives its “Connected” state text from `routeState` alone, so contradictory published values can yield “Connected” plus `controlConnected == false` (`Shared/Connectivity/BoothConnectionPresentation.swift:23-42`, `58-66`).

There is also a latent stale-label case: `publishDisconnected()` clears connection/authentication state but leaves `pairingState` untouched, while the settings fallback maps `.authenticated` to the text “Connected” (`Shared/Connectivity/BoothTransport.swift:341-362`; `iPad/UI/iPadConnectionSettingsView.swift:225-263`, `374-391`). Repository call-site search found no production caller of `publishDisconnected()` (only its declaration and `Tests/MessageTests.swift:396`), so this is not evidence for the observed reconnect sequence; a regression should still prevent a disconnected status from rendering that fallback as connected.

Minimal policy: keep `preferredPeerID` and its trusted display name as the stable identity anchor; treat Bonjour presence as freshness/availability only. Prefer a valid non-empty discovered name when it is present, otherwise retain trusted metadata, and never substitute a device ID into the primary customer-facing name. Render a persistent preferred-peer row for as long as the preference exists; represent discovery as “Searching”, “Not found”, or “Unavailable” only when transport/browser state distinguishes those conditions. Drive connection wording from one status policy: use the existing `vm.isAuthoritativeControlReady` for the affirmative “Connected” state, show `.connecting` as “Reconnecting” with the preferred identity retained, and show preview/asset readiness separately so loss of a secondary channel does not imply control loss. Align any shared resolver's text and boolean from the same authoritative predicate.

## Existing tests and deterministic regression cases

`Tests/BoothConnectionPresentationTests.swift` is built against the Mac test target and covers disconnected, route-connecting, route-connected, and fallback values (`Tests/BoothConnectionPresentationTests.swift:1-132`). Its connected case sets `.connected` and connected route state together; it does not test preferred identity persistence, transient discovered-list clearing, stale names, mismatched state/route, or iPad UI labels.

`iPadTests/iPadSmokeTests.swift` verifies view-model observation forwarding (`iPadTests/iPadSmokeTests.swift:90-121`), constructs customer content across phases (`246-279`), and checks authentication/secure/freshness/full-readiness gates (`281-326`). It does not construct/assert `iPadConnectionSettingsView` output or exercise discovery/reconnect presentation. `Tests/MessageTests.swift:379-404` checks that `publishDisconnected()` clears current peer identity, but not preferred/discovered state or the resulting settings wording.

Add focused deterministic regressions around a pure iPad connection-presentation policy, then one hosted-view check if practical:

1. Seed preferred ID plus trusted display name; publish connected; publish `.connecting` with nil live peer identity and an empty discovered list; assert the same preferred ID/name remains visible and status says “Reconnecting”, not “Not connected” or “Connected”.
2. Republish discovery with the selected ID absent, then present, then absent; assert the preferred row identity/name stays stable while only availability changes. Include two route provenances so removal from one route does not remove a peer still observed on the other.
3. Feed absent/empty Bonjour `deviceName` and UUID-shaped ID while a trusted display name exists; assert the customer-facing preferred/nearby title never becomes the raw ID. Also test the generic-name case when there is no trusted name.
4. Assert empty discovery distinguishes active, failed, and completed/no-result states rather than always “Searching”.
5. Assert “Connected” requires the selected peer, authenticated secure control, and fresh control activity. Assert a stale timestamp, disconnected/connecting state, wrong peer, or route/state mismatch cannot yield the positive label; independently assert preview/asset loss only changes their readiness rows.

Use fixed peer IDs and explicit `publishControlActivity(at:)` timestamps around the 10-second boundary. These cases preserve current discovery/transport behavior and test presentation invariants without attributing the protocol disconnect to this audit.
