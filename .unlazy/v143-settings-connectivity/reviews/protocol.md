# v1.4.3 trusted-control protocol audit

## Scope and conclusion

Source audit snapshot taken before remediation, comparing `HEAD c6647ce` with `remotes/origin/fix/v1.4.2-stability-pairing`, focused on the requested control transport files and tests. The findings below describe the pre-remediation code unless the implementation follow-up says otherwise.

The exact first malformed frame **cannot be named from the supplied evidence**: this task has no packet capture, frame bytes, or incident log payload. The current runtime rejection records `Invalid control frame: <localized error>` and closes the candidate; it does not record which frame bytes caused the error (`BoothNetworkTransportRuntime.swift:1268-1303`). Do not change frame acceptance or secure-channel rules until the first failing frame is captured.

The normal **Mac inbound** and **iPad outbound trusted** paths both use `BoothNetworkTransportRuntime` as the connection and protocol owner. The apparent legacy Mac `accept` path is bypassed: `NetworkBoothTransport.startListener` starts the core listener for Mac control and returns before constructing its older listener (`NetworkBoothTransport.swift:3087-3112`); the runtime listener dispatches accepted sockets directly to `startInboundControlConnection` (`BoothNetworkTransportRuntime.swift:662-730`). I found no code evidence that a valid first encrypted control message should be rejected on this single-owner path. Because the exact failing frame is unavailable, the incident cause remains undetermined.

### Listener-path disambiguation

The legacy listener code later in `startListener` contains an `isMacControlListener` branch that would call `startInboundControlConnection` and then `accept` (`NetworkBoothTransport.swift:3140-3182`). It is not the normal Mac control route: the earlier `if channel == .control, role == .mac` block calls `transportRuntime.startControlListener(...)` and returns at line 3111. The active runtime listener itself admits and starts the candidate (`BoothNetworkTransportRuntime.swift:716-729`). Therefore the legacy `accept`/`configure` double-reader concern is not ranked as an incident hypothesis for the current Mac control listener.

The active runtime uses a per-candidate `NWConnection`, decoder, and secure channel (`BoothNetworkTransportRuntime.swift:102-155`, `1261-1318`). In production, `NetworkBoothTransport` constructs its runtime and control write pump on the same `transportQueue` (`NetworkBoothTransport.swift:441-454`); bootstrap frames are sent directly by the candidate on that queue (`BoothNetworkTransportRuntime.swift:2077-2101`), and the shared control writer is bound at promotion (`1998-2025`). The first operational control messages then go through the bound pump. Across the inspected sources, the control-specific `NWConnection.send(content:)` sites are this direct bootstrap sender and `BoothControlWritePump.flush` (`BoothControlWritePump.swift:151-172`); `NetworkBoothTransport.send` delegates to the pump or runtime enqueue (`5717-5733`). The other direct send sites are preview/asset channel writers and use their own channel connections. The inspected call sites do not show a second control receive loop or third control writer on the active runtime listener path.

## Framing, coalescing, and crypto state

- The wire frame is an 8-byte header (`PR`, version, channel, big-endian `UInt32` length) followed by payload. The parser supports partial data and loops over all complete frames in one append; control payloads are capped at 256 KiB (`BoothTransport.swift:1306-1367`, `1372-1384`). `NWConnection.receive` asks for up to 64 KiB (`BoothNetworkTransportRuntime.swift:1261-1265`), so multiple control frames may be returned together.
- If one parser append contains valid frame(s) and then an invalid header/length, `append` throws before returning its accumulated frame array. The caller therefore cannot deliver earlier frames from that callback, and the runtime rejection message does not identify whether the bad bytes were the first frame or a later coalesced frame (`BoothTransport.swift:1328-1367`; `BoothNetworkTransportRuntime.swift:1268-1303`).
- The runtime passes a whole receive buffer to `decoder.decode`, which parses and decodes all frames before the caller handles the returned array (`BoothTransport.swift:1420-1455`; `BoothNetworkTransportRuntime.swift:1268-1279`). The decoder’s plaintext-bootstrap decision uses the mutable `handshakeComplete` flag, which the runtime updates only while handling Ready (`BoothNetworkTransportRuntime.swift:1932-1935`). Therefore, on one receive callback, every frame is decoded against the pre-callback completion flag. A coalesced Ready plus a valid encrypted app frame can decode because the key channel is already configured and `open` is attempted for non-bootstrap payloads; normal frame coalescing alone is not evidence that the first encrypted message is malformed. The reverse boundary—plaintext bootstrap coalesced after a Ready—deserves a focused test because decoding occurs before the flag flips.
- “Configured” and “established” are distinct in the runtime: keys configure after both secure Hellos; establishment/promotion requires both Ready directions and verified Ready proof (`BoothNetworkTransportRuntime.swift:1850-1871`, `1874-1945`). `BoothSecureChannel.isConfigured` means keys/session exist (`BoothPairing.swift:808-823`); it is not itself the application authorization gate. Candidate app controls before trusted/secure promotion are rejected by `handleCoreMessageOnQueue` (`BoothNetworkTransportRuntime.swift:1321-1400`). No plaintext operational fallback is present in this path.
- The operational writer serializes its own pending control items and protects secure messages before framing (`BoothControlWritePump.swift:92-133`, `151-200`). Candidate bootstrap sends are direct, plaintext sends before promotion (`BoothNetworkTransportRuntime.swift:2077-2101`). The standard Mac inbound and iPad outbound runtime paths bind the shared writer at promotion and send later application controls through it. The code does not by itself prove send reordering on either single-owner path.

`NetworkFramingTests` covers split frames, multiple parser frames in one append, and separate calls before/after handshake completion (`Tests/NetworkFramingTests.swift:60-78`, `226-240`). It does not cover a coalesced secure Ready plus first encrypted application message, or a plaintext bootstrap frame coalesced after Ready. `NetworkRouteTests` exercises the runtime listener, iPad outbound authentication, and a first secure control send (`Tests/NetworkRouteTests.swift:1425-1500`, `1600-1674`); that matches the core ownership path but does not force the target `NWConnection.receive` callback to return a specific coalesced batch.

## Connection generations and socket close

Runtime trusted outbound connections and inbound admissions allocate generations and attach them to the candidate (`BoothNetworkTransportRuntime.swift:1116-1150`, `2514-2559`). On the active Mac core-listener path, admission sets the runtime's active generation directly (`2541-2559`); the facade adopts that generation after authenticated promotion (`NetworkBoothTransport.swift:1044-1081`). The legacy `confirmInboundControlAdmission` path can replace the active generation (`BoothNetworkTransportRuntime.swift:2603-2624`), but the active core listener bypasses it. Candidate callbacks match the candidate object, connection identity, and candidate generation; authenticated facade events require the facade's owned/current generations (`BoothNetworkTransportRuntime.swift:2153-2161`; `NetworkBoothTransport.swift:716-727`).

Runtime parser/crypto rejection calls `connection.cancel()`, removes the candidate, clears the matching active/probe slot, and emits a generation-tagged rejected event (`BoothNetworkTransportRuntime.swift:2164-2209`). For an adopted connection, facade send failures invalidate the runtime-owned generation, and the close event is ignored unless that generation still owns the facade (`NetworkBoothTransport.swift:465-478`, `1007-1018`). These guards constrain stale callback effects; they do not identify which frame in one coalesced batch failed.

The identity-probe admission lane is handled inside the runtime listener too (`BoothNetworkTransportRuntime.swift:716-729`, `2444-2565`). The `confirmInboundControlAdmission` branch that returns `false` for probes belongs to the legacy facade bridge (`2603-2617`); because that bridge is bypassed on the active Mac listener path, I do not treat it as a current trusted reconnect failure.

## Ranked hypotheses

1. **A later frame in one coalesced receive is malformed and gets reported only as a generic decode failure (medium as a diagnostic lead; incident cause unknown).** `BoothFrameParser.append` may parse earlier frames and then throw on a bad trailing header without returning the frame list. That makes the error insufficient to name the first malformed frame and does not identify what produced it.
2. **The first encrypted frame is valid but arrives with a protocol or crypto mismatch (low/unknown).** A `BoothSecureChannel.open` failure, counter mismatch, or a Message decode failure would close the candidate, but there are no bytes/logs to distinguish them. The inspected single-owner runtime does not establish such a mismatch.
3. **A Ready/application coalescing boundary is the cause (low for valid encrypted app control; confirmed pre-fix edge for plaintext bootstrap).** Ready followed by a correctly sealed application frame is decodable with the already-configured channel. Before remediation, a plaintext secure bootstrap after Ready in the same receive could pass the decoder’s pre-callback `handshakeComplete == false` decision and reach the negotiator. This source-level gap is not evidence that a valid encrypted first message is malformed.

Excluded false lead: the legacy Mac facade `accept` branch appears to double-own a control socket when read in isolation, but the active Mac control listener returns before it. It should not be used to explain this incident unless another caller is shown to reach that branch.

## Narrowest next diagnostic

Before changing a decode/acceptance rule, capture one failing Mac-inbound session with both TCP directions and correlate it to the control connection generation. At the transport boundary record, for that connection only: role, normal-vs-identity-probe admission, generation, connection identity, decoder identity, each receive byte count, frame header/channel/length, frame order, decoder error type, secure-channel configured/Ready/established booleans, and each control send’s message case plus plaintext/secure flag. Preserve the failing frame bytes in a controlled local capture (avoid adding general-purpose plaintext payload logging); hash/redact unrelated application payloads. This is the evidence needed to name the first bad frame and distinguish a malformed/trailing frame from an authentication, crypto, or message-decode failure.

The original incident still needs a trusted iPad outbound session into the actual Mac runtime control listener with the safe diagnostics below; source inspection cannot name the frame. The implementation adds deterministic decoder coverage for Ready plus encrypted heartbeat in one receive and rejects a plaintext bootstrap on the next buffered frame after Ready. The new 100-cycle trusted runtime loopback covers repeated secure activation, heartbeat, and application-control delivery, but it does not reproduce the unavailable physical incident frame.

## Implementation follow-up

The active runtime and facade-owned control receive path now parse one control frame, apply its protocol transition, then parse the next buffered frame. The decoder remains fail-closed and reports symbolic parser/crypto errors with safe frame metadata. The original supplied evidence did not include a packet capture, raw frame, or populated incident log, so the exact first offending frame and cause remain unproven; the added diagnostic event is intended to capture that evidence on the next failure.
