# Dedicated Keychain Persistence Check

This opt-in probe checks whether a signed Mac test host can read a harmless test value after rebuilding. It uses the fixed service `com.nont.prcphoto.release-test-keychain` and account `operator-pin-rebuild-probe`; it never reads, writes, or deletes the production Admin PIN or pairing services.

The probe is disabled unless `PRC_RUN_REAL_KEYCHAIN_PERSISTENCE_TEST=1` is set. Its phases are `write`, `read`, and `cleanup`. The stored marker is test data, not a credential.

## Debug to Debug

Use the same effective signing identity and Keychain access group as the Mac app. Do not run `xcodegen` over a checkout with local signing overrides. Run the `write` phase, quit Xcode if it launched the test host, then run `read` from a fresh DerivedData path:

```sh
TEAM_ID_FROM_XCODE='<the local Team ID configured in Xcode>'
env DEVELOPER_DIR='/Applications/Xcode-26.6.0.app/Contents/Developer' \
  PRC_RUN_REAL_KEYCHAIN_PERSISTENCE_TEST=1 \
  PRC_KEYCHAIN_PERSISTENCE_PHASE=write \
  /Applications/Xcode-26.6.0.app/Contents/Developer/usr/bin/xcodebuild \
  -project PRC-PhotoBooth.xcodeproj \
  -scheme PRC-PhotoBoothTests \
  -destination 'platform=macOS' \
  -derivedDataPath .build/keychain-persistence-debug-a \
  -configuration Debug \
  -only-testing:PRC-PhotoBoothTests/KeychainHelperTests/realKeychainPersistenceProbe() \
  DEVELOPMENT_TEAM="$TEAM_ID_FROM_XCODE" \
  CODE_SIGNING_ALLOWED=YES CODE_SIGNING_REQUIRED=YES test
```

Run the same command with `PRC_KEYCHAIN_PERSISTENCE_PHASE=read` and a fresh path such as `.build/keychain-persistence-debug-b`. A passing test means the exact marker survived the rebuild and the test host could read it from the preferred Keychain store.

The local generated project may assign a Team ID to the Mac app while leaving the test bundle unset. If Xcode refuses to load the test bundle because the host and bundle have different Team IDs, pass the same local Team ID with the command-line `DEVELOPMENT_TEAM` setting as shown above. Keep that value in local Xcode settings or the shell only.

## Debug to Release and Clean Build

Repeat the write phase from Debug, then read using `-configuration Release` and a new DerivedData path. Add `ENABLE_TESTABILITY=YES SWIFT_ACTIVE_COMPILATION_CONDITIONS=DEBUG` to that Release test invocation because the current test source uses Debug-only test hooks. This keeps the Release configuration and signing entitlements while enabling the test harness; build the normal Release app separately without these overrides. For a clean Debug check, use a new path for the second Debug invocation. Record the effective code signature and entitlements for both built app products with `codesign -dv --verbose=4` and `codesign -d --entitlements :-`; compare bundle identifier, signing team, `application-identifier`, and `keychain-access-groups` shapes.

Run the `cleanup` phase after the matrix. If Xcode cannot launch the test host under the intended signature, treat the integration check as inconclusive and retain its exact build/signing error. Do not substitute the production Admin PIN service.
