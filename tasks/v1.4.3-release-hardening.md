## Finding Status

### A01 — DSLR cross-guest recovery privacy (P0)

- **Root cause:** A failed transfer discarded the capture context needed by Retry Receive. Recovery then lacked the identity of the shutter attempt and could fall through to a “latest media” path.
- **Fix:** Separate active and recoverable attempt contexts; retain immutable request-time, baseline file names and handles, camera identity, and freshness bounds after recoverable failure. Invalidate that context at explicit lifecycle boundaries. Validate media discovered through filesystem polling, PTP ObjectAdded, and the fixed Sony PC buffer against the same attempt. Baseline acquisition fails closed.
- **Invariant:** A transfer with unproven camera identity or freshness is rejected; older guest media is never selected as a fallback.
- **Tests:** DSLRCaptureAttemptTests covers recovery-context lifecycle, camera identity, baseline acquisition, stale filenames/handles, late transfer, object-added freshness, PC-buffer behavior, finite camera clock offset normalization, and ordered quarantine reset. All tests passed in the final 612-test Xcode 26.6 Mac run.
- **Manual verification:** Still required with a Sony ZV-E10 containing older SD-card images: fail transfer, Retry Receive, Retake, disconnect/reconnect, and power-cycle. Confirm no prior guest image is displayed or persisted.
- **Status:** Implemented — focused automated tests passed on Xcode 26.6 — physical Sony verification pending.

### A02 — Authoritative finalization transaction (P1)

- **Root cause:** The UI and durable manifest could disagree after finalization enqueue failure; reconciliation could omit desired jobs or accept jobs from a stale generation.
- **Fix:** Persist FinalizationPlan and its transaction ID with the manifest; batch the desired job bundle; enforce transaction ownership at execution and dependency checks; reconcile missing jobs without rolling a finalizing manifest back to capturing. Preserve ambiguous print submissions as operator-resolved unknown outcomes. Legacy manifests and uncertain legacy print jobs are handled conservatively.
- **Invariant:** One completed capture sequence has one authoritative finalization generation. Old jobs cannot operate on current content or satisfy current dependencies. UI remains processing after durable finalization.
- **Tests:** FinalizationTransactionTests, JobQueueStoreTests, JobRecoveryTests, SessionRecoveryTests, and SessionJobQueueTests cover durable intent, transaction mismatch, repair, dependency isolation, required-job recovery, and unknown print behavior. All tests passed in the final 612-test Xcode 26.6 Mac run.
- **Manual verification:** Force quit during capture, finalizing, render, upload, and print; restart and inspect manifest/job ownership. For uncertain CP1500 submission, verify operator resolution and no automatic duplicate.
- **Status:** Implemented — focused automated tests passed on Xcode 26.6 — full suite and physical restart/print fault verification pending.

### A03 — Production transport recovery off MainActor (P1)

- **Root cause:** The transport facade is MainActor-isolated. Previously, a Mac control listener handed sockets to MainActor before admission, and reconnect timer expiry handed off before creating and starting a replacement socket.
- **Fix:** The Mac control listener now reserves/rejects a single control slot on the Network queue, starts accepted sockets there, and expires unadopted admissions with a bounded queue timer. A cached reconnect route now creates and starts the replacement NWConnection on that queue, retries at most five times, and times out sockets that remain waiting or are not adopted within ten seconds. Control socket failures release the slot on the Network queue.
- **Invariant still open:** Route discovery/browser result selection and its initial browser-driven connection still cross MainActor. The production UI/authentication facade also adopts the started connection on MainActor. These paths need further ownership work and device verification.
- **Tests:** productionListenerAdmissionIsQueueOwned proves a real loopback listener can accept a second connection after its first unadopted admission expires during a MainActor stall. productionReconnectStartsSocketOffMainActor proves a cached replacement socket reaches a real loopback listener during a MainActor stall. The latest focused NetworkRouteTests (39 tests) and BoothPreAuthPolicyTests (16 tests) passed after the timeout adjustment; the complete 612-test Mac suite also passed on Xcode 26.6.
- **Manual verification:** Block MainActor while dropping Wi-Fi/Ethernet and confirm browser-driven route discovery, authentication, and recovery with the production iPad. Confirm waiting/retry behavior across Wi-Fi and wired Ethernet.
- **Status:** Partially fixed — listener admission and cached socket start are automated on the Network queue — browser discovery and physical verification remain P1 release blockers.

### A04 — Trusted reconnect under pre-auth abuse (P1)

- **Root cause:** A global anonymous pre-auth failure ceiling can prevent an iPad from reconnecting after a LAN flood. Trust decisions must not rely on claimed Bonjour identity or source IP.
- **Fix so far:** Admission state and the limiter run on the Network queue. A single identity-probe opportunity remains available when the anonymous global ceiling is reached. The hello's claimed peer ID selects a per-trusted-ID retry budget, so a paired iPad can probe from a changed DHCP address without relying on its old endpoint cache. The claim does not authenticate; existing secure negotiation and stored-secret HMAC proof remain mandatory. Successful authentication clears the ID budget; repeated failed claims trigger bounded cooldown.
- **Invariant still open:** This change proves an admission opportunity and claimed-ID throttling, not that authentication completes off MainActor or that a real paired iPad recovers after an app restart/address change during an active hostile flood. The identity-probe state is in memory and resets across process restart; the changed-address test models an empty endpoint cache after restart.
- **Tests:** `trusted identity probe works with empty endpoint history and a changed DHCP address`, `spoofed trusted IDs exhaust only their identity-probe retry budget`, and `spoofed trusted identity probe is throttled by claimed peer ID` exercise anonymous pre-auth admission failures, empty endpoint history/new address, and spoofed-ID quota. BoothPairingTests continue to cover real HMAC acceptance/rejection. A real-listener integration combining 100 invalid peers, app restart/DHCP change, and stored-secret HMAC remains pending.
- **Manual verification:** With a paired production iPad, send at least 100 invalid pairing/authentication attempts, then reconnect using both its previous and a changed address. Confirm the stored-secret proof succeeds and anonymous clients remain throttled.
- **Status:** Partially fixed — queue-owned admission and known-endpoint recovery are tested — cryptographic identity-probe and 100-attempt production integration remain a P1 release blocker.

### A05 — Customer display authority and recovery

- **Root cause:** Fresh-session and recovered-session flows had inconsistent decisions about whether an iPad or external viewer was authoritative.
- **Fix:** CustomerDisplayAuthority applies one authority matrix to none, iPad-only, external-only, and dual-display configurations.
- **Invariant:** A session advances only through the authoritative display path available for its current state.
- **Tests:** CustomerDisplayWorkflowTests covers the authority matrix. Recovery integration should be exercised with the physical display matrix during device testing.
- **Manual verification:** Test iPad only, external display only, both, and neither during fresh start and recovery.
- **Status:** Implemented with matrix test coverage. Physical display/recovery checks pending.

### A06 — Authoritative guest delivery endpoint (P1)

- **Root cause:** Choosing the first or lowest-numbered private interface can select a VPN/bridge or the wrong link when Wi-Fi and Ethernet are both active.
- **Fix:** Model a typed endpoint containing interface name/index/type/address/port. Automatic selection fails closed when multiple candidates remain. Duplicate path entries merge deterministically by interface identity; generic plus concrete classification keeps the concrete type, while conflicting concrete Wi-Fi/Ethernet classification becomes ambiguous. Explicit Wi-Fi, Ethernet, or interface choices constrain resolution; supported direct-Ethernet addresses are considered only for the Ethernet choice and never override a known Wi-Fi type. Coordinator QR, preflight, and job execution use the same selection. Unavailable or ambiguous local HTTP contributes no URL to QR policy.
- **Invariant:** No localhost, arbitrary private interface, or interface-name heuristic is emitted in a guest QR. When route identity is uncertain, local delivery is unavailable.
- **Tests:** GuestDeliveryEndpointResolverTests covers ambiguous paths, duplicate merge, classification conflict, explicit Wi-Fi/Ethernet, direct Ethernet, interface identity, port, and unavailable resolution. SessionQRCodePayloadResolverTests covers loopback/insecure failures. All tests passed in the final 612-test Xcode 26.6 Mac run.
- **Manual verification:** Test Wi-Fi only, Ethernet only, both, VPN active, VM interfaces installed, route change, and the actual guest network adapter. Scan each QR from a guest device.
- **Status:** Implemented with fail-closed resolution — automated tests passed on Xcode 26.6 — physical network matrix pending.

### A07 — Bounded local HTTP admission and recovery (P2)

- **Root cause:** A large number of simultaneous sockets could consume server resources; per-client state could outlive the connection or fail to release on timeout.
- **Fix:** Lease-token admission enforces global and per-client caps; IPv4-mapped IPv6 addresses normalize to the same client identity. A lease is released exactly once when a request completes, fails, or times out. Slow/no-data requests have a bounded timeout and overflow receives 503.
- **Invariant:** One guest cannot exhaust all local HTTP slots indefinitely; lease accounting cannot underflow or retain idle client records.
- **Tests:** LocalWebServerTests includes production HTTP overflow/route checks, raw slow-client timeout cleanup, exact-once lease release, global cap, and address normalization. All tests passed in the final 612-test Xcode 26.6 Mac run.
- **Manual verification:** Exercise 20–50 concurrent guest downloads and slow clients while confirming normal health and guest routes recover.
- **Status:** Implemented — automated tests passed on Xcode 26.6 — physical load verification pending.

### A08 — Duplicate NWPath interface crash (P0)

- **Root cause:** Network path snapshots can contain more than one interface record with the same identity. Building a dictionary with unique keys traps the Mac process when duplicates arrive.
- **Fix:** Merge incrementally by stable interface index and name. Identical types deduplicate; generic plus concrete classification keeps the concrete type; conflicting concrete Wi-Fi/Ethernet types resolve as ambiguous and disable local guest delivery.
- **Invariant:** Repeated or duplicate path records never crash route updates, and conflicting classification never produces a guest QR.
- **Tests:** GuestDeliveryEndpointResolverTests covers duplicate entries, both generic/concrete arrival orders, conflicting classification fail-closed, stale snapshot replacement, and known Wi-Fi at configured direct-LAN IP.
- **Status:** Fixed in code and automated coverage; physical route-change matrix pending.

## Concurrency Audit

- `BoothNetworkTransportRuntime` owns connection slots, generations, reconnect timers, identity-probe state, endpoint history, and admission counters on its serial Network queue. `onQueue` uses a queue-specific key to avoid self-deadlock. Connection callbacks compare both object identity and generation before mutating state. The facade still uses MainActor for route discovery, hello handling, and authentication progress; this is the open A03/A04 boundary.
- `NetworkBoothTransport` owns protocol and pairing state on MainActor. Network callbacks hop to MainActor and validate active connection/generation or receive-token identity before applying frames. Pre-auth timeout and socket cancellation remain queue-owned. MainActor stalls can still delay discovery and initial authentication.
- `BoothPreAuthWatchdog` protects its deadline state with `NSLock`. `BoothPreAuthAdmissionLimiter` is only mutated by the runtime's serial queue. No new detached tasks were introduced.
- `GuestDeliveryPathInterfaceTypes` receives `NWPathMonitor` updates on its dedicated serial queue and swaps a value snapshot under `NSLock`; readers receive a locked copy. Duplicate interface merge occurs before publication, so conflicting snapshots fail closed without touching shared state.
- `DSLRCameraSource` owns attempt and PTP-quarantine state on MainActor. ImageCaptureCore session-open and device-ready callbacks are documented on the main thread; PTP event callbacks explicitly hop to MainActor. Capture tasks recheck camera identity, attempt ID, and cancellation after suspension. Physical device sequencing remains unverified.
- `BoothCoordinator` owns soak-run IDs and publication state on MainActor. Route refreshes carry a generation and reject stale refresh results. End-of-run cleanup quiesces jobs before removing isolated remote artifacts; failed cleanup preserves local evidence and records an error.

The audit found no new shared-state race in the modified queue-owned paths. The remaining transport issue is ownership placement across the MainActor boundary, tracked as P1 in A03/A04 rather than treated as solved by the runtime tests.

## Event Readiness / Soak

The Settings screen now exposes three explicit modes:

- **Synthetic Benchmark:** generated images, isolated scratch files, compositor timing, and locally claimed/completed benchmark queue records. It says that it does not validate the production workflow.
- **Camera Hardware:** requires the selected live camera and rejects demo mode. It captures real images and fails on capture errors; it creates no customer sessions.
- **Production Pipeline:** requires a live BoothCoordinator, active event, ready camera and customer display, available production persistence, settled queue, server, and an unambiguous configured guest delivery path. It uses the current event's template and photo count, starts origin-tagged sessions, accepts captures through the ordinary review handler, finalizes through the production transaction/queue, and verifies configured delivery.

Production sessions carry origin=soakTest, soakRunID, and soakCycleIndex. Normal session starts and active-event switches are blocked while the run owns the booth. Active-run route publication is restricted to that run's manifests. At run end, remaining soak sessions are removed from the gallery and local server routes; failed/cancelled session evidence remains on disk. Automatic deletion checks origin, run ID, completed status, and active run, then removes only that soak session's workspace, queue records, manifest, and local session record. A cleanup failure is recorded and local diagnostic evidence is retained.

Cloud upload is an explicit Production Pipeline option using the current production connection settings, but files and the temporary public alias use a validated `.soak/<runID>` namespace separate from customer paths. Safe per-session remote cleanup removes only that run's alias, staging directory, and published versions; failure is surfaced and local evidence is retained. Physical printing is disabled by default and only available in Production Pipeline. When enabled, confirmation states the maximum job count and interval; cycle 1 and then every Nth cycle submit real print jobs. The production cycle fails if an explicitly scheduled print or requested cloud job is not present and successful.

Outcomes distinguish passed, failed, stoppedEarly, and cancelled. Only all requested, error-free cycles can pass. Subsystem coverage labels unexercised hardware as NOT TESTED. RSS is reported as baseline/peak/final and growth; the report does not infer that no leak exists. Camera reconnects are run-scoped when a live coordinator is supplied. iPad model compatibility and the physical event network are not established by simulator or synthetic tests.

Automated runner coverage does not replace a hardware-backed production soak. SoakTests exercises synthetic benchmark execution, missing hardware/coordinator rejection, queue claiming, stop/cancel outcomes, report coverage, and legacy mode decoding. An end-to-end 500-session production soak remains unrun.

### Findings and changes

- **Authenticated-control stall:** Established control receive decoded and counted a frame, then awaited its MainActor delivery before continuing buffered frame decoding and scheduling another socket read. During the exact stall, the reproduced baseline was activity 1, timeout 1, close 1. After secure handshake completion, control frames now decode in order on the transport queue, update liveness only for the current connection/generation, and enter a bounded 256-event stream for MainActor consumption. If that stream fills, the current socket is cancelled and queued events from its generation are suppressed. Handshake/bootstrap frames still cross MainActor for their existing sequential protocol transitions; browser discovery and initial authentication are therefore not claimed to be MainActor-independent.
- **PIN gate sizing:** The Settings window now opens at 420×580 points with a 380×580 minimum, while the gate lets explanatory copy wrap and reserves visible space for all four keypad rows, Cancel, and Touch ID. PIN errors offer Retry/Reset/Cancel and reset requires explicit confirmation. Impeccable detection returned no findings for the touched Settings/PIN views. Screenshot, accessibility, and multilingual geometry review remain pending.
- **Keychain status semantics:** The previous optional-data API treated `errSecItemNotFound` and Keychain infrastructure failures alike. Credential lookup now distinguishes `.found`, `.notFound`, `.unavailable(OSStatus)`, and `.malformed`. Setup is offered only for a genuine not-found result. Unavailable or malformed records fail closed; wrong-PIN verification does not migrate or overwrite a credential; reset is explicit. The local built Debug and Release app signatures use the same bundle identifier and matching team-prefixed `application-identifier` / `keychain-access-groups`. This does not prove what happened to the user's prior production PIN: its service was not deliberately queried by this work.
- **Pairing Keychain:** Pairing secrets share the same generic Keychain layer. The store now preserves trusted metadata on unavailable reads, dual-reads Data Protection and legacy copies, retains the fallback source, avoids overwriting a conflicting copy, and reports success only when the effective read returns the requested secret. A failed Data Protection update cannot replace an older effective legacy/Data Protection secret.
- **Secure-channel regressions:** Existing per-frame sequential bootstrap transitions and plaintext downgrade, authentication ordering, replay, malformed-envelope, binding, and stale-generation tests passed in the final Mac suite. The added receive path applies only after the decoder reports handshake completion.

Networking flow before:

```text
socket receive -> decode frame -> await MainActor delivery -> decode/read next frame
```

Networking flow after:

```text
socket receive -> queue-owned authenticated decode and liveness -> continue receive
                                              \\-> bounded event stream -> MainActor application delivery
```

Keychain state before: `Data?` collapsed missing, inaccessible, and invalid credentials. After: `found(value)`, `notFound`, `unavailable(status)`, and `malformed` remain distinct through PIN and pairing decisions.
